# xtatic — Claude context

Static-site generator: MDX in, plain HTML out. The MDX is compiled and executed at build time; the output is pure HTML with no client-side runtime. See `README.md` for the user-facing description.

## Pipeline

`src/cli.js` → `src/index.js` `build()` → `src/paths.js` (resolve logical paths) → `src/registry.js` (lazy-compile through a per-build cache) → `src/compile.js` (MDX `compile`+`run`, with `recma-imports.js` rewriting user `import`s into resolver calls) → `src/tree.js` (assemble + apply defaults) → `src/render.js` (walk layout chain) → write to `fs`.

Each module is small and focused; read the source rather than relying on this map.

## Non-obvious invariants

- **`fs` is dependency-injected** through `build({inputDir, outputDir, fs})` for `.md`/`.mdx` reads and all writes. `.js` reads are *not* injected — they go through Node's real `import()` (see below). Memfs-only tests therefore can't reference `.js` files; tests that need `.js` use real-fs scratch dirs under `./test-tmp/<slug>/`.
- **Zip files are read as if they were directories.** `index.js` wraps the injected `fs` once via `wrapZipFs` from `src/zipfs.js` before passing it to any registry. Any path containing a `.zip/` segment (e.g. `/fonts/Inter.zip/Inter-Regular.ttf`) is intercepted: the prefix-up-to-`.zip` is read from the underlying fs, decompressed once via `fflate.unzipSync`, cached for the build's lifetime, and the rest of the path is looked up as an entry name. The interception covers `fs.readFileSync` and `fs.promises.readFile` only — `readdir`, `stat`, `writeFile`, etc. are passed through unchanged (no current call site needs them on zip-internal paths). Caveats: split happens at the *first* `.zip/` in the path, so nested zips aren't supported; matching is case-sensitive (`.ZIP` won't trigger); a literal directory named `*.zip/` will be misinterpreted as a zip and error.
- **`outputDir` is owned by the build, but NOT wiped upfront — writes are skip-if-unchanged, and stale files are pruned at the end.** All output writes (pages in `index.js` `writePages`, shared `_assets/` in `assets.js` `writeAll`, co-located files in `assets-plain.js` `writeAll`) flow through one `createOutputWriter({fs, outputDir})` per build (`src/output.js`), created from the RAW injected fs *before* `wrapZipFs` (comparison reads of output files must not hit the zip interception). `writer.writeFile(absPath, data)` stats the existing file, compares size then bytes, and skips the write when identical — preserving mtimes for rsync/HTTP-caching consumers. `writer.prune()` (called last in `buildImpl`) deletes every file under `outputDir` not recorded by a `writeFile` this build, then rmdirs emptied directories — this is what makes renames/deletes Just Work now that there's no upfront `rm`. Shape conflicts from a previous build's layout are handled: a directory sitting where a file must go is `rm -r`'d in `writeFile`, and `ensureDir` stat-*verifies* after `mkdir -p` (memfs's recursive mkdir silently no-ops over an existing file where Node throws EEXIST), walking the prefix chain to remove a conflicting file. Consequences: a *failed* build leaves the previous output intact (prune only runs after all writes), and the two registries take an optional `writer` (defaulting to a private one for registry-only unit tests; only `buildImpl`'s shared writer ever prunes). `assertSafeOutputDir` in `index.js` still rejects `outputDir` of `/`, `.`, or anything that is the same as or an ancestor of `topDir`/`inputDir`/`layoutsDir` so a misconfiguration can't nuke source (prune deletes unrecognized files). There is no opt-out; the only non-generated bytes under `outputDir` are verbatim-directory copies (see the `.xtatic-verbatim` invariant below), which flow through the same writer.
- **The build is two-pass when assets are involved.** `index.js` `renderTree` walks the module tree synchronously to collect `{outPath, html}` for every page (so `<Image>`, `<Style>`, `<Font>`, and the recma-assets-injected `__xtatic_asset` calls have already fired and recorded jobs into their respective registries). Then `await imageRegistry.processAll()`, `await styleRegistry.processAll()`, `await plainAssetRegistry.processAll(pages)`, and `await fontRegistry.processAll(pages)` run in series. The plain-asset registry needs `pages` because its placement chooser scans each page's rendered HTML for tokens to derive the per-asset reference graph (which pages contain which tokens) before deciding inline vs shared vs co-located. The font registry needs `pages` to resolve auto-subset text (see `<Font>` below). Plain-asset runs *before* font (since commit 2 of the font-subset work) so the font registry can call `styleRegistry.cssForPage(html)` / `plainAssetRegistry.cssForPage(html)` and get back the resolved CSS reaching each page — the css-static cascade engine consumes that pair. Substitute *composition* order is independent of `processAll` order (the four substitutes are still composed in the same order; token namespaces are disjoint). `await assetRegistry.writeAll()` flushes everything under `outputDir/_assets/`, then `await plainAssetRegistry.writeAll()` flushes co-located files at their source-tree-mirroring positions. The four `substitute` closures are composed and applied to each page's HTML before `writeFile`, then wrapped by `assetRegistry.relativize(…, path.posix.dirname(outPath))` as the OUTERMOST step — `substitute(html, outPath)` is page-aware (co-located URLs need `outPath`, and the final relativize needs the page dir to resolve the `__XTATIC_EMIT_…__` placeholders the four substitutes leave behind for shared `_assets/` files). Token namespaces are disjoint (`__XTATIC_IMG_<hex>__`, `__XTATIC_STYLE_<hex>__`, `__XTATIC_FONT_<hex>__`, `__XTATIC_ASSET_<hex>__`), so substitute order doesn't matter for correctness.
- **All emitted assets go through a shared `createAssetRegistry`.** `src/assets.js` exposes `emit(bytes, ext)` (sync, idempotent on `${hash}.${ext}` filename — same bytes with different ext gets two files, but same bytes+ext is dedupe-emitted once), `relativize(text, fromDir)`, and `writeAll()` (batched mkdir+writeFile at end of build). `index.js` constructs one per build and threads it into `createImageRegistry`, `createStyleRegistry`, and `createPlainAssetRegistry`. **The shared-assets dir name is configurable** via `createAssetRegistry({…, assetsDir})` (default `'_assets'`), sourced from `build({assetsDir})` ← `pkg.xtatic.assetsDir`. `assertValidAssetsDir` in `index.js` constrains it to a single path segment (non-empty, no `/`, not `.`/`..`); the only consumer of the name is `assetRegistry` itself (co-located plain assets mirror the source tree, not this dir, so they're unaffected). **A page may not write into the assets dir:** `renderTree` computes `assetsDirAbs = outputDir/assetsDir` and throws (hard error) if any page's `outPath` is at-or-under it — checked before the page-vs-page `seen` collision. This guards both the default and custom names; without it a page named `_assets` (or an `outputPath` of `/_assets/…`) would silently share the directory (different filenames → no clobber, but a namespace overlap, and an exact `<hash>.<ext>` match would clobber since pages write after `writeAll`). **`emit` does NOT return a final URL.** It returns an opaque placeholder `__XTATIC_EMIT_<hash>.<ext>__` — a fifth token namespace, disjoint from the four registry tokens. The real file still lives at `outputDir/_assets/<hash>.<ext>`, but the URL pointing *at* it is computed **relative to whatever file contains the reference** by `relativize(text, fromDir)`, which rewrites each placeholder to `path.posix.relative(fromDir, assetOutAbs)`. That's what keeps the output free of root-absolute `/_assets/…` URLs, so a site works served from any subpath — there's no `basePath` config and none is needed. `relativize` is called from three sites: (1) `index.js`'s composed substitute, fromDir = the page's own output dir, as the OUTERMOST wrapper after all four registry substitutes have run; (2) `assetRegistry.writeAll()` itself, fromDir = `_assets/`, so an emitted CSS file's url() refs to sibling assets collapse to bare `<hash>.<ext>` — only `ext==='css'` emissions are relativized (css-urls is the sole producer that embeds placeholders into bytes, and binary must not be utf8-round-tripped); (3) `plainAssetRegistry.writeAll()`, fromDir = the co-located file's dir. Co-located plain assets bypass `_assets/` and write to their source-tree-mirroring positions via `plainAssetRegistry.writeAll()`; their *own* URL is computed directly by the plain-asset substitute (not via the placeholder). Net: every output URL is relative (page-relative for direct refs, relative-to-CSS for url() refs inside emitted/co-located CSS) or `data:` (inline). No build cache across runs — every rebuild re-emits.
- **`Image` (`xtatic:image`)** — `src/image.js` `createImageRegistry({fs, topDir, assetRegistry, defaultInlineThreshold})` is built per-build and threaded through `createRegistry` so the resolver can hand each importer its own `Image` component (closure captures `importerAbsPath`, identical to `readfile` shape — `/foo` against topDir, otherwise against the importer's dir). Sharp is `import('sharp')`-loaded lazily on first job, with a clear "run npm install sharp" error if absent — it's an optional peerDep so non-image projects don't pay the install cost. SVG sources skip sharp entirely (passed through verbatim, content-addressed under their own hash). Job dedup key is `${absSrc}|${JSON.stringify(opts)}`; final `<img>` HTML is composed per-call from the job result + that call's pass-through attrs (with `className → class`, attribute escaping done in `image.js`'s own `escAttr`/`renderAttrString` since the substituted tag bypasses the JSX runtime).
- **`cssForPage` cross-registry seam.** `styleRegistry.cssForPage(html)` and `plainAssetRegistry.cssForPage(html)` each return the rewritten CSS text of every CSS source that reaches `html` (style: every `<Style src>` whose token appears; plain-asset: every `<link rel=stylesheet>` whose stylesheet-kind token appears — non-stylesheet `.css` refs like `<link rel=preload as=style>` are excluded). Both must be called after the owning registry's `processAll()` — that's where the CSS bytes are read and `rewriteCssUrls`-rewritten into the closure-scoped `resolvedCss` map. Results are deduped by source absPath (two tokens to the same file → one entry). The font-cascade engine consumes the pair as the union of "all CSS that this page sees," ignoring whether a given stylesheet is inlined, shared, or co-located — only the text matters for cascade analysis.

- **`Style` (`xtatic:style`)** — `src/style.js` `createStyleRegistry({fs, topDir, assetRegistry, defaultInlineThreshold})` is shaped exactly like the image registry (same per-importer factory, same path-resolution rules, same token/substitute pipeline). `<Style src="...">` reads the CSS and runs `rewriteCssUrls` from `src/css-urls.js`: a regex pass over `url(...)` tokens that resolves each to `/foo` (against topDir) or `./foo`/`../foo` (against the source CSS's dir), reads the bytes, and emits them via `assetRegistry.emit`. Any scheme-prefixed URL (`data:`, `http(s):`, …), `//`, or `#` is passed through verbatim (same scheme regex as `assets-plain.js`). Below the inline threshold (default 2KB) the rewritten CSS is emitted inline as `<style>…</style>` at the call site; above, it goes to `/_assets/<hash>.css` and the call site gets `<link rel="stylesheet" href="…">`. Pass-through attrs (`media`, `nonce`, `crossorigin`, etc.) land on whichever tag is emitted, with `className → class`. The plain-asset pipeline reuses the same `rewriteCssUrls` for `.css` files reached via plain `<link rel=stylesheet>`, so the implementation is shared (only the not-found error wording differs, passed in by the caller). Caveats: `@import "…"` (bare-string form) is NOT rewritten — only `url(...)` tokens are; if your inline CSS legitimately contains `</style>` it will prematurely close the tag (no escape attempt yet). `rewriteCssUrls` does NOT transcode `.ttf`/`.otf` references — they emit as-is, hashed. The transcode behavior moved to `<Font>` (see below); a hand-rolled `@font-face { src: url('./x.ttf') }` inside a `<Style>`-loaded CSS file ships the TTF verbatim now.
- **`Font` (`xtatic:font`)** — `src/font.js` `createFontRegistry({fs, topDir, assetRegistry, fontSubset, transcode, subset})` is shaped like the image/style registries (per-importer factory, dedup'd jobs, token+substitute pipeline) but designed for `<head>` use: each call expands to a `<style>@font-face{…}</style>` plus an optional `<link rel="preload" as="font" type="font/woff2" href="…" crossorigin>` when `preload`. Source handling, in priority order: if `text` is given **or** auto-subset is on for the call, the source is **subsetted** to just the code points in question (via `src/font-subset.js` `subsetToWoff2`, lazy `import('subset-font')` — HarfBuzz/WASM; new optional peerDep alongside `sharp`/`wawoff2`) and emitted as WOFF2 regardless of input ext; else `.ttf`/`.otf` are transcoded to WOFF2 via `src/font-transcode.js` (`transcodeToWoff2`, lazy `import('wawoff2')`); else `.woff`/`.woff2` pass through verbatim. Both `font-transcode.js` and `font-subset.js` serialize their calls through a module-local `queue` because each wraps a singleton WASM instance whose heap is shared across calls. The `transcode` and `subset` constructor args default to the real loaders and are overridable by tests (`test/font.test.js` stubs both). **Auto-subsetting** is opt-in: `fontSubset: true` on `build()` / `pkg.xtatic.fontSubset` enables it for every `<Font>` in the build (resolves to `{ mode: 'css-static', precision: 'face' }` — the css-aware face-precision mode is the default). Pass an object for explicit control: `{ mode: 'all-text' | 'css-static', precision: 'family' | 'face' }`. The per-call boolean `subset` prop overrides that default (`subset={true}` opts one font in even without the global flag; `subset={false}` opts one out when global is on). Explicit `text=` always wins over auto-subset on the same call. Two modes exist: `mode: 'all-text'` takes the union of all rendered text across all pages (`scope:'site'`; `<script>/<style>/<template>` content is stripped, the four JSX-runtime entities are decoded; intentionally over-includes a touch). `mode: 'css-static'` (the default when `fontSubset: true`) goes through `src/font-cascade.js` `computeCodePointsByFace({pages, getCssForPage, registeredFaces, precision})` — parses each page with `parse5`, gathers CSS via the cross-registry `cssForPage` seam plus inline `<style>` blocks in the HTML, walks the DOM top-down resolving `font-family`/`font-weight`/`font-style`/`font-stretch` (UA defaults for `b`/`strong`/`h1`-`h6`/`em`/`i`/`code`/`kbd`/`pre`/`samp`; pseudo-classes evaluated always-true as an over-include hedge; `font:` shorthand parsed), matches each text run against the union of declared faces (`<Font>` calls + `@font-face` rules from user CSS, via family fallback chain + closest-weight/style scoring + variable-font weight-range absorption + `unicode-range` filtering), and attributes the rendered code points to the matched face. `precision: 'face'` (default) keys glyph sets by `(family, declared-weight-range, style, unicodeRange)`; `precision: 'family'` collapses to family only. Known gaps in v1: `::before`/`::after` `content:` is not extracted (icon fonts driven that way won't be attributed — hedge:'full' in commit 4 makes this byte-bloat instead of tofu); `font-weight: bolder/lighter` rounds to fixed steps rather than walking the spec's relative-table; `:not(...)`/`:nth-child(...)` evaluate always-true. The cascade engine never under-includes for elements the cascade can see; an unmatched face (no glyphs attributed) falls back to transcode-only (safe). **Hedge / complement subsets (commit 4):** `fontSubset.hedge: 'none' | 'latin1' | 'full'` controls a *second* emitted `@font-face` rule per call carrying the *complement* of the primary subset (the source font's coverage minus the kept glyphs, optionally capped to U+0000-U+00FF for `'latin1'`). Both faces share family/weight/style and get disjoint `unicode-range` descriptors — the browser then partitions code points: characters in the primary fetch the small primary asset, anything else fetches the complement only on demand (zero JS, zero perf cost on the common path). This is what makes `'full'` the never-tofu default for the boolean form `fontSubset: true` (which expands to `{mode:'css-static', precision:'face', hedge:'full', preloadHedge:false}`); the explicit-object form `{mode: ...}` defaults hedge to `'none'` (treat the explicit form as "I'm being deliberate"). `fontSubset.preloadHedge: false | 'prefetch' | 'preload'` adds an extra `<link>` for the complement (default off; lazy `unicode-range` fetch happens regardless). Source-font coverage is read once per `absSrc` via `fontkit.create(bytes).characterSet` (cached per build); the helper is injectable via the `getCoverage` constructor option so stub-byte tests can sidestep fontkit. User-supplied `<Font unicodeRange>` disables hedge for that one call (treat as explicit user intent). Hedge skips any call that wouldn't be subsetted anyway (no primary → no complement). `fontkit` is a hard dependency. **Scope (commit 5):** `fontSubset.scope: 'site' | 'page'` (default `'site'`). `'site'` is what every commit so far did — one shared subset per face across the whole build (better cross-page HTTP caching, smaller total bytes). `'page'` issues per-`(call, page)` subset jobs sized to that page's text only — minimal first-paint bytes, but the same `<Font>` call in a layout produces a different asset URL per page it renders into. Implementation: the cascade engine returns `Map<pageOutPath, Map<faceKey, Set<cp>>>` always; font.js merges across pages for `'site'` and uses the per-page maps for `'page'`. The page-aware substitute keeps a `tokenToHtmlByPage` map and is called as `fontSubstitute(html, outPath)` (the composed substitute in `index.js` was already passing `outPath` through to the asset substitute; the font slot now consumes it too — pre-`'page'` calls that ignore the second arg keep working). Per-page bucket assignment uses the same token-scan trick as the plain-asset registry: `page.html.match(TOKEN_RE)` tells us which (call, page) combos to emit jobs for. Pages with identical resolved glyph sets dedupe through the same `${absSrc}\0${subsetText}` job key as `'site'` mode.

- **Token-bleed guard (commit 5):** before scanning page text for glyph attribution (in either `mode:'all-text'` or `mode:'css-static'`), font.js strips ALL xtatic tokens (`__XTATIC_(IMG|STYLE|FONT|ASSET)_<hex>__`) from the html. Otherwise the tokens themselves — they're plain ASCII at scan time, before substitute runs — would attribute their characters (`X`, `T`, `A`, `I`, `C`, `F`, `_`, hex digits) to whatever face the body resolves to, polluting the kept glyph set. The cssForPage seam still receives the ORIGINAL (token-bearing) html so it can find style/asset tokens; only the cascade/text walk sees the stripped copy. font.js pre-resolves cssForPage and bakes the result into each page object as `page.css` before handing it to the cascade engine, so the engine doesn't need to know about the token-strip dance. **Dedup-timing inversion (commit 1):** unlike image/style, font jobs are built *inside* `processAll(pages)`, not eagerly during render — auto-subset text isn't knowable until the scan completes. Each `<Font>` call pushes onto a `calls` array (capturing `absSrc`, family/weight/style/displayed metadata, optional `text`, the `autoSubset` flag, and a `currentStack()` context snapshot); `processAll(pages)` computes `autoSubsetText` once (`computeAutoSubsetText` defaults the mode to `'all-text'` if a per-call `subset={true}` opted in without any global config), then derives each call's `subsetText` (explicit `text` → canonicalize; else `autoSubset` → the computed union; else undefined) and groups calls into jobs keyed by `absSrc` (no subset) or `${absSrc}\0${subsetText}` (subset). Other font metadata (family/weight/style/etc.) is still per-call and lives in the assembled `<style>` block, not the asset bytes. Always emits via `assetRegistry.emit` (no inline-as-data: URL — fonts are large and the embed is awkward); always shared `/_assets/<hash>.<ext>`, no co-located placement and no per-call inlineThreshold. Props: `src` and `family` are required; `family` is CSS-string-escaped (backslash + quote) and rejected if it contains `<` (defense against `</style>` injection in the assembled tag). `weight` accepts number or string (e.g. `"100 900"` for variable-font ranges); `style`/`display` are validated against the standard sets; `unicodeRange` is passed through to `unicode-range:` verbatim; `text` must be a non-empty string when present; `subset` is a boolean. Unknown extra props throw — `<Font>` does not silently pass-through arbitrary attrs (no clean place to route them across two emitted tags). Same `</style>`-in-CSS caveat as `<Style>` (no escape attempt). Token namespace `__XTATIC_FONT_<hex>__`, disjoint from the other three.
- **Plain `<img>`/`<link>`/`<script>`/`<source>`/`<audio>`/`<video>`/`<a>`/`<area>` are auto-processed.** The recma-assets plugin (`src/recma-assets.js`) walks every compiled JSX call and rewrites whitelisted `(tag, attribute)` pairs so the value flows through `__xtatic_asset(value, opts)`. It catches both shapes MDX/JSX produce: direct `_jsx('img', {src})` and `_jsx(_components.img, {src})` (markdown's `![]()` and `[]()` lowering — MDX maps tag names through `_components`). Whitelist: `img.src`, `script.src`, `source.src`, `audio.src`, `video.{src,poster}`, `link.href` (only when `rel` is statically one of `stylesheet`, `icon`, `shortcut`, `apple-touch-icon`(`-precomposed`), `mask-icon`, `preload`, `prefetch`, `modulepreload`, `manifest` — non-asset rels like `canonical` are skipped because their hrefs aren't files), and `a.href`/`area.href` (no rel guard). Dynamic `<img src={x}>` works because `__xtatic_asset` is a runtime check: non-strings, empty strings, and passthrough URLs are returned verbatim — any value matching the RFC 3986 scheme regex `^[a-zA-Z][a-zA-Z0-9+.-]*:` (`data:`, `http(s):`, `mailto:`, `tel:`, `javascript:`, `blob:`, …) plus `//` and `#`; `./a:b.pdf` is still a path because it doesn't start with a letter. `css-urls.js` uses the same rule for `url(...)` values. **`asset()` is idempotent on its own tokens** (`ANY_XTATIC_TOKEN_RE`): a manual `<a href={asset('./x.pdf')}>` would otherwise be double-wrapped now that `a.href` is whitelisted, so a value that already *is* an `__XTATIC_(ASSET|IMG|STYLE|FONT)_<hex>__` token is returned as-is. **`?query`/`#fragment` suffix is split off before path resolution** and re-appended to every resolved URL (page-relative, co-located, shared, inline — appended inside the per-call resolver closures); a pure `?x` value (no path) is passthrough. **Page-link rewriting (the `<a href>`/`<area href>` case):** `assets-plain.js` `processAll(pages)` builds `pageOutBySrc` (`page.srcPath → page.outPath`; `srcPath` is stamped onto each page record by `renderTree` as `path.posix.join(topDir, mm.__xtatic_path)`). If a call's resolved `absSrc` is a known page source, the entry is flagged via `entry.targetPageOut` (not `undefined`): byte read, css-rewrite, and placement are all skipped, and the token resolves to `cleanPageUrl(path.posix.relative(pageOutDir, targetOut)) + suffix` — page-relative, with `cleanPageUrl` stripping a trailing `/index.html` to a directory URL (`about/`) and mapping a same-dir `index.html` to `./` (`outputPath`-override targets like `feed.xml` are linked as the literal file). A non-page target (`./report.pdf`) has `targetPageOut === undefined` and flows through the normal byte-read + placement chooser. Links resolve against the *source* file's location (like `import`/`readfile`), so source siblings `a.md`/`b.md` link via `./b.md` and come out as `../b/` because each renders into its own output dir. Per-call escape hatch: `data-xtatic-placement="inline|shared|co-located|auto"` overrides the auto chooser; the recma plugin extracts it from the props at compile time and removes it from the output (so it doesn't leak into HTML). recma-assets also reads the JSX call site out of the `_jsxDEV` `source` argument and threads it (as `tag`/`locFile`/`locLine`/`locColumn` opts) into `__xtatic_asset`, so `asset()` can put a `<img> at file:line:col` frame on the render-context trace for the deferred not-found / collision errors. The `auto` chooser per source file: size ≤ `defaultInlineThreshold` (default 4KB) → inline as `data:` URL; else if used by exactly one page AND the asset's source path is at-or-below that page's output directory → co-located (mirrored to its *inputDir*-relative position under `outputDir` — the same mapping pages and verbatim copies use; the registry takes `inputDir` for this, defaulting to `topDir` for registry-only tests. Path *resolution* of a leading `/` is still topDir-rooted, so `/assets/x.png` beside `pages/` resolves fine but can never co-locate — `colocatedOutPath` returns null for anything outside inputDir); else → shared (`/_assets/<hash>.<ext>`). Inlined `.css` referenced from `<link rel="stylesheet">` is a special case: the substitute pass replaces the whole `<link …>` tag with `<style …>CSS</style>` rather than emitting `data:text/css`, transferring all attributes except `rel`/`href` (so `media`, `nonce`, `class`, etc. carry over). recma-assets signals this by passing `{kind:'stylesheet'}` to `__xtatic_asset` for stylesheet links; only stylesheet-kind tokens trigger the tag-level rewrite, so the same CSS file referenced from a non-stylesheet `<link>` (e.g. `rel="preload"`) still gets the data: URL treatment. Same caveat as `xtatic:style`: a literal `</style>` substring in the CSS prematurely closes the inlined tag. Co-located is the only placement whose URL is computed *inside* the plain-asset substitute: `substitute(html, outPath)` computes it via `path.posix.relative(pageOutDir, assetOutAbs)`. Shared placement instead emits an `__XTATIC_EMIT_…__` placeholder that the outer `assetRegistry.relativize` pass (in `index.js`) turns into a page-relative URL — so both end up relative, just resolved at different stages. Conflicting explicit placements for the same source file throw; `co-located` requested where not viable throws. The asset registry's substitute pass HTML-escapes `&` and `"` since the substituted URL goes inside an existing `src="…"` attribute (the JSX runtime escaped the surrounding context, but the token itself bypassed escaping). Reference graph is derived post-render by regex-scanning each page's HTML for tokens — no page-tracking plumbing during render. The `__xtatic_asset` runtime closure is captured into a top-level `const __xtatic_asset = arguments[0].__xtatic_asset;` injected by recma-assets so it's reachable from inside `_createMdxContent` (where `arguments` refers to props, not the runtime). Inject only happens if a rewrite occurred. Order in `compile.js`: `[recmaImports, recmaAssets, recmaSelf]` — recma-self's pre-declare picks up the injected const, so it's not added to the destructure-from-`__xtatic_self`.
- **Verbatim directories: a `.xtatic-verbatim` marker file opts a subtree out of the pipeline.** `src/verbatim.js` owns the marker name (`VERBATIM_MARKER`) and the collect/write helpers. `index.js` `walkPages` checks each directory's dirents for the marker *before* descending: a marked directory is not walked for pages; instead every regular file under it (recursively, marker files excluded) becomes a `{absPath, relPath}` verbatim entry, and `walkPages` now returns `{pages, verbatim}`. Verbatim entries never touch `hasPlaceholders`/`resolveLogicalPath`/the registry/`assembleTree` — they are not modules, have no `__xtatic_path` or `url`, and produce no tree node (so `childPages` listings don't see them). `buildImpl` stamps `v.outPath = outputDir/relPath`, rejects any under `assetsDirAbs`, and pre-seeds `renderTree`'s `seen` map with `verbatim file "<rel>"` labels so a page landing on the same `outPath` throws (message reads `Two sources write…` when the prior claimant is verbatim, `Two pages write…` otherwise). Bytes are copied at the end via `writeVerbatimFiles` through the shared output writer (after `writePages`, before `prune()`), so skip-if-unchanged and prune apply: removing a file or the marker itself cleans the stale output. **Link resolution:** `buildImpl` passes `processAll(pages, {verbatimOutBySrc})` (absSrc → outPath) to the plain-asset registry, which records `entry.targetVerbatimOut` next to `targetPageOut`; `isLinkTarget(entry)` covers both and short-circuits byte-read/css-rewrite/placement exactly like page links. Both go through `cleanPageUrl` (`index.html` → `dir/`); other verbatim filenames are kept literally. **Directory links:** `findLinkTarget(absSrc, pageOutBySrc, verbatimOutBySrc)` tries the direct hit first, then treats `absSrc` as a directory and probes `index.html`/`index.md`/`index.mdx` in the page map and `index.html` in the verbatim map (`PAGE_INDEX_NAMES`) — `resolveSrc` already strips a trailing `/`, so `href="foo/"` and `href="foo"` both resolve to `<dir>/index.*`'s output URL. No index → falls through to the byte-read, where `EISDIR` is caught and reported as `"foo/" is a directory with no index page`. This applies to every whitelisted attr, so `<link rel=stylesheet href="./legacy/site.css">` stays a `<link>` to the copied file (never inlined, never re-emitted under `_assets/`) — and, consequently, its CSS is invisible to `cssForPage`/the font-cascade engine (it's opaque bytes). `import`/`readfile`/`<Image>` of a file under a marker still work normally (explicit "process this" requests; the marker only governs the walker). `lint.js` `walkLintTargets` skips any directory containing the marker (`fs.existsSync`, real-fs only, like the rest of lint). `watch` needs nothing: it already watches `topDir` recursively. **Pattern markers (per-file granularity):** a marker whose text has any non-blank, non-`#` line is a *pattern* marker. `parseVerbatimMarker(text)` returns `{all: true}` for the empty/comment-only case (everything above applies unchanged) or `{all: false, rules}` where each rule is a compiled gitignore-subset glob (`*` within a segment, `?`, `**` across segments; no `/` → basename match at any depth via a `(?:.*/)?` prefix; a `/` anywhere else → anchored to the marker dir, leading `/` stripped; trailing `/` → `dirOnly`; no negation). Both walkers (`walkPages` in `index.js`, async via injected fs; `walkLintTargets` in `lint.js`, sync real-fs) carry an `active` stack of `{baseRel, rules}` down the recursion — one entry per pattern marker on the path — and test each dirent with `isVerbatimByPatterns(active, childRel, isDir)`, which rebases `childRel` (walk-root-relative: inputDir for pages, topDir for lint) onto each marker's own dir. A matching directory goes through `collectVerbatimFiles` (whole subtree, same as an empty marker); a matching file becomes one verbatim entry; the marker file itself is always skipped before matching so `*` can't copy it. Non-matching entries continue as normal (pages are pages), so a pattern marker at the inputDir root is fine — the intended home for `favicon.ico`/`robots.txt`. Everything downstream (`outPath` stamping, assetsDir rejection, `seen` collision labels, `verbatimOutBySrc` link resolution, `writeVerbatimFiles`, prune) sees the same `{absPath, relPath}` shape and doesn't know which kind of marker produced an entry. Scope cuts: only directories under `inputDir` are considered; no `!` negation.
- **Keep-going mode collects errors instead of throwing them; `src/errors.js` owns the collector.** `build({keepGoing: true})` (← CLI `-k`/`--keep-going`, parsed for `build`/`watch`/`serve`/`browse` and rejected elsewhere) creates one `createErrorCollector({keepGoing})` per build in `build()` and threads it as `errors` into `buildImpl` and all four asset registries (constructor option, defaulting to a strict collector for registry-only unit tests). The contract is `errors.report(err)`: in strict mode it *throws* `err` (so every call site behaves exactly as the old `throw`), in keep-going mode it records and returns. Errors are deduped by object identity — this is why `registry.js` now caches a failed load as `{status:'failed', error}` and rethrows the *same* Error object to every later importer (`cachedOrThrow`/`markFailed`), and why `loadLayoutByName` caches not-found errors by name in `failedLayouts`: a broken layout shared by fifty pages is listed once. Per-unit boundaries in `buildImpl`: page load (dropped from `entries` before assembly, so its tree slot becomes synthetic), the stray-`getPages` check, each generator's expansion, logical-path collisions (`uniqueLogicalPaths` drops the later claimant), each page's layout-chain resolution (page kept in the tree for listings but added to `unrenderable`, skipped by `renderTree`), each page's render (`renderTree` takes a `ctx` object now; `renderPage` pushes the `{page, outPath, srcPath, html: null}` record *before* rendering so a failed page still claims its output path — otherwise a link to it would fall through to the plain-asset registry and copy its `.md` source as an asset), and each registry job (a failed job leaves its calls' tokens unresolved; `writePages` then skips any page whose substituted HTML still matches `LEFTOVER_TOKEN_RE`). `pages` records with `html: null` exist only in keep-going mode; `assets-plain.js` `processAll` skips scanning them (but still records their `srcPath → outPath`), and `buildImpl` passes only `rendered` pages to the font registry and `writePages`. If every page fails to load, `buildImpl` returns early (no assembly, no prune) so "No page sources found" doesn't bury the real errors; otherwise prune runs as normal. `build()` renders each collected error's context trace, then throws `makeBuildError(errors, skippedPages)` — an `AggregateError` with `xtaticKeepGoing: true`, `errors`, and `skippedPages` (sorted, deduped logical labels) whose message numbers every error and ends with the not-written list; a fatal (non-per-unit) throw out of `buildImpl` is folded in as the last entry. Strict mode throws `errors.list[0]` — the same object it always threw. `cli.js`/`watch.js` also make lint non-fatal under the flag: lint runs, its error is held, the build runs, and `combineErrors(lintError, buildError)` joins them (lint first). A parse error is therefore reported twice under `-k` (once by lint with its code frame, once by the build's compile error) — accepted noise.
- **`.html` input files are pages, processed by `src/html.js` — not MDX.** `walkPages` in `index.js` picks up `.html` alongside `.md`/`.mdx` (same logical-path mapping: `foo/bar.html` → `foo/bar/index.html`, collisions with a same-slot `.md` throw); `registry.js` `loadHtml` reads the file once and runs `processHtml(source, {asset, importerDisplay})`: parse5 (`sourceCodeLocationInfo: true`) walks the DOM (including `<template>` `.content`) and routes every whitelisted (tag, attr) reference through the same per-importer `asset()` that recma-assets wires up for MDX. The whitelist data lives in `src/asset-rules.js` (`ASSET_TAG_ATTRS`, `ASSET_LINK_RELS`, `VALID_PLACEMENTS`, `classifyLinkRel`), shared by recma-assets.js, html.js, and assets-plain.js so the front ends can't drift. **Output is the original source with surgical splices** (attr spans from parse5 source locations), not a re-serialized DOM — comments, doctype, whitespace, and quoting ship byte-identical. A rewritten attr is re-emitted `name="token"` (double-quoted; parse5 hands over entity-decoded values, and asset() returning the value unchanged — passthrough/empty — means no edit, preserving original bytes). A stylesheet `<link>`'s `rel` is also re-emitted double-quoted when its href was rewritten, because the `<link>`→`<style>` inline substitute in assets-plain strips `rel="…"`/`href="…"` by double-quote regex. `data-xtatic-placement` is extracted + removed (valid values only, mirroring recma); element start line/col + tag ride into asset() as loc opts, so deferred not-found errors read `in <img> at page.html:2:1` — note asset() fires at *load* time here (before renderTree), so `currentStack()` is empty and that synthesized frame is the whole trace. The module shape: `mm.default = () => ({html})` (sync, processed once per build), `mm.layout = null` — a `.html` page is a complete document, and null (not undefined) opts it out of assembleTree's defaultLayout walk — `mm.title` from the first non-empty html-namespace `<title>` (the frontmatter analog; beats the name-derived default), plus the usual `__xtatic_path`/`url` stamps, so html pages participate fully in `childPages`/page-link rewriting. `.html` is importable from `.md`/`.mdx`/`.jsx` (recma-imports' `SPEC_RE` and its whole-module default-binding regex both include it; the lint resolver needs no change since specs carry the extension). Page generators can't be `.html` (buildImpl throws on a `{placeholder}` `.html` filename), `.html` files have no exports (no `outputPath`, no `getPages`, no frontmatter), and lint skips them (`SOURCE_EXT_RE` unchanged). **Inline CSS is processed too (html.js only, not MDX):** every `url(...)` in a `<style>` element's text or a `style=""` attribute goes through the same per-importer `asset()`, tokenized by `findCssUrls` exported from `css-urls.js` (the same regex `rewriteCssUrls` uses, so the two front ends agree on what a url() is). `<style>` text is rewritten on the raw *source span* of the text node (`source.slice(startOffset, endOffset)`), not `node.value` — parse5 normalizes CRLF in text values, so value offsets don't map back onto the source. A rewritten reference is re-emitted `url("token")`; a passthrough one keeps its bytes. The error frame for a `<style>` url() carries the CSS line/column of the token (`in <style> at page.html:3:20`), computed by `lineColAt`; a `style=""` url() reports the element's start. `data-xtatic-placement` is taken lazily per element (`takePlacement`) so the same override covers the element's whitelisted attrs, its `style=""`, and (for `<style>`) its text, and an element that produced no reference keeps the attr. The substitute pass HTML-escapes the resolved URL (`&`→`&amp;`), which is right inside `style=""` and harmless inside `<style>` for every URL the pipeline mints (data:, hashed, relative) — but a user `?a=1&b=2` suffix inside `<style>` would come out `&amp;`. Known gaps (parity with the MDX whitelist): `srcset`, `<base href>`, and the bare-string `@import "…"` form aren't processed; `url()` inside a literal `<style>` block in `.md`/`.mdx` still isn't either.
- **Build-time errors carry a render-context trace.** `src/render-context.js` keeps a module-level stack of frames describing what's currently rendering: `{kind:'page', page, file}` (pushed by `index.js` `renderTree`), `{kind:'layout', file}` (pushed per layer by `render.js`'s wrapper closures), `{kind:'module', file, atFile, atLine, atColumn}` (an imported `.md`/`.mdx`/`.jsx` rendered as `<Tag/>` or as `{children}`), and `{kind:'component', name, atFile, atLine, atColumn}` (a function component like `<Font>`/`<Image>`). Rendering is fully synchronous, so a plain module-level stack is safe. `jsxDEV` (the dev JSX runtime, see the cheat sheet) pushes the component/module frame with the call-site `source = {fileName, lineNumber, columnNumber}` and `attachContext(err)`s any throw; `render.js`'s layout wrappers and `jsx-runtime.js`'s `renderChild` module branch do the same. For work *deferred* past render — `<Font>`/`<Image>`/`<Style>` jobs and the `__xtatic_asset` placement pass, whose errors fire in their registries' `processAll()` long after the stack unwound — each call snapshots `currentStack()` onto its job and passes it back to `attachContext(err, snapshot)` when the deferred work throws. Plain `<img>`/`<link>`/… don't go through `jsxDEV` (they're string elements, no frame), so `recma-assets` reads the call site out of the `_jsxDEV` `source` argument and passes it (plus the tag name) into `__xtatic_asset` opts; `asset()` synthesizes the matching `component` frame on top of its snapshot. `attachContext` is idempotent (first/deepest writer wins). `build()` wraps the whole pipeline and folds `formatContext(err.xtaticContext, {readSource, codeFrameWidth})` (deepest-first, like a JS stack trace) into `err.message`, so every consumer — cli, watch, serve-error — shows it. `formatContext` is also where the line-numbered call site (`in <Font> at layouts/default.mdx:5:3`) comes from. **Each located frame also gets a source code frame.** For every `module`/`component` frame carrying an `atFile`/`atLine` (the call site), `formatContext` reads that source and prints `renderCodeFrame(...)` (from `src/code-frame.js`) indented 4 spaces under the frame line — the same ±2-context, color-highlight/caret, line-windowed frame the lint phase prints (lint and render-context share `code-frame.js`; the simpler single-line `codeFrame` in `registry.js` for *compile* errors is separate and unchanged). The source bytes come from `readSource`, a sync best-effort reader `build()` builds from its `fs` + resolved `topDir` (`makeSourceReader` in `index.js`): it resolves the frame's display path against `topDir` (absolute paths pass through), `readFileSync`s, memoizes, and returns null on any miss (→ no frame). `codeFrameWidth` (← `build({codeFrameWidth})` ← `pkg.xtatic.codeFrameWidth`, the same knob lint uses) defaults to `120` in the render path; `formatContext` with no opts (its default) renders frames *without* code frames, so unit tests calling it directly are unaffected.
- **Load-phase errors split into "compile" vs "evaluate".** A module's body is `compile`d/parsed and then *run* (`new AsyncFunction(...)` in `compile.js`/`compile-jsx.js`). A throw from running it — a top-level `export const x = f()` whose `f()` threw, often a function imported from a `.js` file — is a *runtime* error, not a syntax error. Both compile modules wrap the `await fn(...)` and tag any thrown object `e.xtaticEvalError = true`; `registry.js`'s `loadMdx`/`loadJsx` catch then routes to `makeEvalError` (label `Failed to evaluate "<file>": <msg>`, plus the surviving user stack frames — `userStackFrames` drops Node internals and any frame under xtatic's own `XTATIC_SRC_DIR`, which includes the eval'd-body wrapper `eval at compileSource (…/src/compile.js…)`, leaving the real throw site like `at boom (…/lib.js:2:9)`; `err.cause` keeps the original) instead of `makeCompileError` (the syntax-error path with line/column + single-line code frame). **No double-wrapping:** both `makeCompileError` and `makeEvalError` set `err.xtaticFormatted = true`, and the catch re-throws any already-formatted error as-is — so a nested import that fails during a parent's body eval surfaces naming the *real* culprit file once (e.g. `Failed to evaluate "c.jsx": …`), not buried under the importer with a duplicated frame. (This eval/compile split is separate from the render-context trace above, which covers errors thrown while *rendering* a page, not while loading a module.)
- **`__xtatic_path` is stamped on every loaded module.** `registry.js` `loadMdx`/`loadJsx` `Object.defineProperty` a non-enumerable `__xtatic_path` (the display path, relative to topDir) on `mm` after compile. Non-enumerable so it stays out of `recma-self`'s bare-identifier set and any `Object.keys(mm)` consumer (`tree.js` etc.). Used by render-context frames and `render.js`'s `layoutLabel`. `.js` modules don't get it (frozen ESM namespaces, and they show up as `component` frames via `type.name` anyway).
- **`url` is stamped alongside `__xtatic_path`.** `registry.js` `stampUrl` defines an *enumerable* lazy getter `mm.url` on every loaded `.md`/`.mdx`/`.jsx` module. On first read it mints `plainAssetRegistry.forImporter(absPath)('/' + __xtatic_path)` — i.e. a deferred page-link asset token pointing at the module's own source — and caches it (so repeated reads, and the same `<a href={p.url}>` rendered into many landing pages via a layout, share one token; the page-link resolver is `outPath`-driven, so one token resolves correctly per landing page). This replaced the old `pageHref` builtin. Lazy via getter so unlinked pages never mint a token (and never pollute `assets-plain`'s `calls`); enumerable for parity with `name`/`title`/`date` and so it survives `{...page}` spreads. **Tool-owned:** defined *after* `Object.assign(mm, compiled)`, so it clobbers any user export named `url` (an override would just defeat the rewrite — same stance as `childPages`/`name`). Because the minted value is an ordinary `__XTATIC_ASSET_…__` token, a bare `url` (recma-self self-reference) and `<a href={p.url}>` (whitelisted attr → wrapped in `__xtatic_asset`, which is idempotent on tokens) both work, and it resolves wherever it lands. A module with `__xtatic_path` but no entry in `pages[]` (a layout, or an imported `.jsx`) has a `.url` that resolves as a *non-page* asset (byte-reads its own source) — degenerate, unchanged from old `pageHref`, nobody does it. If `plainAssetRegistry` is absent (some registry-only unit tests), the getter is identity and returns the root-absolute `/<path>` string.
- **`childPages`, `name`, `parent`, `prevSibling`, and `nextSibling` are rewritten by the tool.** `childPages` is overwritten on every module with a freshly built sorted Array of direct children; `name` is set on every non-root module to its last path segment; `parent`/`prevSibling`/`nextSibling` are assigned (unconditionally, `undefined` at the ends and on the root) from the sorted `childPages` in a pass right after the sort, so they're consistent with `childPages` order and are correctly rebuilt by the second assembly pass of the generator flow (a first-pass "last sibling" can gain a `nextSibling`). All three are plain enumerable props (bare identifiers via recma-self, survive spreads) and create reference cycles (`child.parent.childPages` includes `child`) — nothing in the pipeline deep-walks or JSON-serializes a module, keep it that way. They're in `GENERATED_INHERIT_EXCLUDE`. Synthetic grouping nodes participate as parents and siblings like any other node. Anything a user file exports under those names is clobbered. Spec-mandated; don't add an "input wins" override.
- **`date` and `title` are *defaulted* from `name`.** `assembleTree` parses each non-root module's name. A leading `YYYY-MM-DD` or `YYYYMMDD` (with month 01-12 and day 01-31, optionally followed by `-rest`) becomes `date`; the remainder (or the whole name when no date prefix) becomes `title` with dashes-to-spaces, run through npm `title` only if the spaced form is all-lowercase (preserves intentional casing like `THIS-is-a-TEST`). Unlike `childPages`/`name`, these are pure defaults — frontmatter or named exports win.
- **Layouts live in `layoutsDir`, not the input tree.** A page's `layout` is set either explicitly (`layout:` in frontmatter — accepts a string path resolved against `layoutsDir`, or a module object via `import`) or by the `defaultLayout` walk: `assembleTree` walks from each module up to the root and uses the first non-undefined `defaultLayout` it finds (starting at the module itself). `index.js` calls `resolveLayoutChain` *after* `assembleTree`, so string values inherited via `defaultLayout` get rewritten to the loaded module too. There's no longer any magic for files literally named `layout.md` in the input tree — those are just regular pages.
- **`childPages` is a plain `Array` sorted by `name`.** `assembleTree` rebuilds it from scratch and explicitly sorts after attach, so iteration order is guaranteed regardless of how `entries` is ordered when passed in. `index.js`'s `writeNode` reads `child.name` to derive the output path segment.
- **Missing tree positions are synthesized, not errors.** A directory with pages beneath it but no `index.md`/`.mdx`/`.html` of its own (the root included) gets a synthetic node from `assembleTree`: `{}` with a non-enumerable `__xtatic_synthetic: true` (non-enumerable so it survives neither `{...page}` spreads nor recma-self's identifier set). Synthetic nodes get `childPages`/`name`/`title`/`date` like real entries (so listings can show them as group headers) but are skipped by the layout-defaulting loop (never rendered → layout is dead weight; the byKey `defaultLayout` walk climbs *through* them since they never export one), and `renderTree` skips output emission (no `computeOutPath`, no collision check, no `pages.push`) while still recursing into their children. They have no `__xtatic_path` and never pass through the registry, so no `url` getter — `p.url` is `undefined` on them, and `getPages()` can't import them (nothing to import). Synthesized fresh on every `assembleTree` call, which makes buildImpl's two-pass generator assembly safe: nothing can hold a reference to a synthetic node across passes. `assembleTree([])` (input dir with zero page sources) still throws (`No page sources found`), the only remaining assembly error.
- **`outputPath` overrides the default `dir/index.html` derivation.** A page exporting `outputPath` (frontmatter or named export) writes to `outputDir + outputPath` instead — useful for `/feed.xml`, `/sitemap.xml`, `/robots.txt`, etc. Validation in `index.js` `computeOutPath`: must be a string, must start with `/` and not equal `/`, must not end with `/`, must not contain `..` segments. Two pages resolving to the same `outPath` (whether via override or default) throw at render time via a `Map` threaded through `renderTree`. Layout still applies — set `layout: null` to opt out (the existing `layout !== undefined` check in `tree.js` already respects `null`). `name`/`childPages`/`date`/`title` are still derived from the source-file tree position, not from `outputPath`. The override only changes where the file is written and (transitively) the relative-URL base for any co-located assets reached from that page.
- **Page generators: one `{placeholder}`-named source → N pages via `export const getPages = () => [...]`.** A file whose *filename* carries `{name}` tokens (e.g. `tag-{tag}.md`) and exports a **function** `getPages` is a generator. `paths.js` `hasPlaceholders` partitions these out of the normal entries in `buildImpl` (it also throws on a placeholder in a *directory* segment — filename-only in v1). **Two-pass tree assembly in `buildImpl`:** the ordinary (non-generator) entries are run through `assembleTree` *before* generators are expanded, then re-assembled (over the full set) afterward. The reason is the headline feature — `getPages()` is called *during* expansion, after that first assembly, so it can `import` a parent page and iterate its `childPages` (or read any tree-derived field: `name`/`title`/`date`/`url`), which only exist post-assembly. The mechanic that makes this work: the registry caches modules by absPath and `assembleTree` mutates those `mm` objects *in place*, so the generator's `import blog from '/…/index.md'` yields the very same live object the first assembly stamped `childPages` onto. The first assembly is guarded by `if (templateFiles.length > 0)` (skip the redundant pass when there are no generators) and is safe to run twice — `assembleTree` rebuilds `childPages` from scratch and the date/title/layout defaults are `=== undefined`-guarded, so the second pass is idempotent on the normal pages and just adds the generated ones. Stratification keeps it acyclic: the first assembly contains only ordinary pages, so a generator never sees another generator's output (the "generators are leaves" rule, now load-bearing rather than incidental). `registry.expandTemplate(tmplMm, absPath, {toRelPath})` validates `getPages` is a function, calls it (wrapping any throw as `Page generator "…" getPages() threw: …` with `cause`), requires the return to be an array, then turns each item into a synthetic child module that flows through the *rest* of the pipeline unchanged (tree placement, name/date/title defaulting, layout chain, `.url`, render-context). Each item is **flat**: it *is* the generated page's exports. Construction per item: inherit the template's own enumerable exports as a base (so the body's bare refs to the file's own exports + `layout`/`defaultLayout` resolve), throw if an item key clashes with an inherited template export (a page field can't shadow a template export), else `Object.assign` the item over the base, `delete child.getPages`, then bind `child.default = (p) => rawOriginal({...p, __xtatic_self: child})`. `rawOriginal` is the *pre-self-injection* compiled default, stashed per-absPath in a `rawDefaults` Map in `loadMdx` (the normal `mm.default` hardcodes `__xtatic_self: mm`, which would point children at the template). `GENERATED_INHERIT_EXCLUDE` = `{name, childPages, url, getPages, default, outputPath}` — never inherited (tool-derived/positional, the trigger export, the rebound render fn, and `outputPath` which must be per-item or all children collide). Note `url` is an enumerable getter, so the exclude-set `continue` must run *before* reading the key or it'd mint a token. The filename is substituted via `paths.js` `substituteFilename(filename, child, {template, index})` reading values from the merged child (item-over-template), validating each is a path-safe single segment; the result becomes the child's `__xtatic_path`/srcPath/`.url` identity (real, unique — this is why generated pages need no "split logical-vs-source" hack). **Code frames still point at the real `tag-{tag}.md`** because the page-level render-context frame is label-only (`fmtFrame` uses `frame.page`, never reads a code frame), while the body's component/module frames carry `atFile` = the VFile path baked in at compile time = the real generator file. **`__xtatic_self` gotcha:** a template-declared `export const X` binds the body's `{X}` to that const lexically (shared across every generated page); a pages item may not also set `X` (clash → error, above), so per-page values live in item-only fields, which are free identifiers and render per-page. **Caveat — two childPages snapshots:** `getPages` sees the first-assembly `childPages` (ordinary pages only); the second assembly rebuilds it to include the generated pages. They differ only if a generated page lands *under* the parent being iterated (e.g. `blog/tag-{tag}.md` reading `blog.childPages`), in which case that parent's *rendered* listing will include the tag pages — place generators elsewhere (`/tags/`) if you don't want that. **Validation in `buildImpl`:** a normal (non-placeholder) file exporting `getPages` throws (with a `placeholderHint`); `expandTemplate` throws on a non-function `getPages`, a `getPages()` that returns a non-array, a non-object item, or an item key that clashes with a template export, and re-labels a throw from inside `getPages()`; `assertUniqueLogicalPaths` (a merged-set version of `resolveLogicalPaths`' check, using each generated entry's `origin` = `"template → substituted"` for messages) catches two items or an item-vs-real-file resolving to the same logical path. v1 scope cuts: filename-only placeholders, generated pages can't themselves be generators (leaves), values used verbatim (no slugify), no literal-brace escape, `getPages` takes no args (no injected collection — import what you need).
- **Frontmatter requires both `remark-frontmatter` AND `remark-mdx-frontmatter`.** The first parses the `---` block; the second turns it into an MDX export. Easy to miss — `compile.js` configures both. Frontmatter keys are then promoted to top-level module properties; named exports win over frontmatter on collisions.
- **User remark plugins run *after* the frontmatter pair.** `pkg.xtatic.remarkPlugins` is read by `cli.js`, threaded through `build()` → `createRegistry()` → `compileSource()`, and appended after `[remarkFrontmatter, remarkMdxFrontmatter]` so user plugins never see the YAML block (it's already an MDX export node by then). Each entry is either a bare string (`"remark-foo"`) or a tuple (`["remark-foo", opts]`); `cli.js` resolves names via `createRequire(topDir/package.json)` so plugins are looked up in the *user's* `node_modules`, not xtatic's. The `build()` API itself takes already-loaded plugin functions/tuples — no resolution there.
- **`remark-smartypants` is on by default at the CLI layer.** `cli.js` prepends it to `remarkPlugins` (so it runs first, after the frontmatter pair inside `compile.js`). `pkg.xtatic.smartypants` controls it: `true`/absent = on with default options, `false` = off, an object = on with that as the plugin's options. The default is wired in `cli.js` only — `build()` itself gets no smartypants unless the caller passes it in. Tests that drive `build()` directly (most of the suite) are therefore unaffected.
- **The layout chain is bounded** at depth 100 in `render.js` to catch self-referential cycles.
- **A module's own properties leak into JSX expressions as bare identifiers.** `recma-self.js` scope-analyzes `_createMdxContent`, finds otherwise-unbound identifiers, and prepends `const { … } = props.__xtatic_self ?? {};`. `registry.js` wraps `mm.default` so every render call passes `__xtatic_self: mm`, and the closure captures the live `mm` (so `childPages`/`layout` added later by `tree.js` are visible). Built-in globals (`Math`, `Array`, …) are filtered out so they don't get accidentally shadowed; novel free identifiers that don't exist on `mm` simply destructure to `undefined`.
- **Builtins are imported explicitly via the `xtatic:` scheme.** `src/builtins.js` exports `html(s) → {html: String(s)}` and `makeReadfile({fs, topDir, importerAbsPath, importerDisplay}) → readfile(spec)`. User code writes `import {html, readfile, asset} from 'xtatic:builtins'`; the resolver in `registry.js` (`makeResolver`) returns a fresh `{html, readfile, asset}` per importer, with `readfile` closed over the importer's path so relative-spec resolution works. `asset` is the same per-importer function that recma-assets wires up under the hood for whitelisted JSX attributes — useful when you need to call it from places the recma plugin can't catch (non-whitelisted attrs, JS expressions, etc.). To link to another page, there is no builtin — read the target page module's `url` property (see the `__xtatic_path`/`url` invariant below), which is itself a deferred page-link token. `recma-imports.js`'s `SPEC_RE` accepts `^xtatic:[a-z][a-z0-9-]*$` so the rewrite to `__xtatic_resolve(spec)` fires — same path used for ordinary user imports. There is no ambient binding in either `.md`/`.mdx` or `.jsx`: omit the import and the name is free for the user to define. `readfile` is sync (JSX expressions render synchronously, so no `fs.promises` here); paths starting with `/` resolve against `topDir`, everything else (including bare names) resolves against the module's own directory — matching POSIX intuition rather than `import`'s npm-flavored "no bare specs" rule. The known set of `xtatic:*` modules and their exports lives in `src/builtins-registry.js` — both `makeResolver` (for the runtime "Unknown builtin module" error) and the lint rule `xtatic/builtin-imports` (for compile-time validation) consume it, so they can't drift.
- **`autoInstall` flips missing optional peer deps from build-time errors to on-demand `npm install`.** `xtatic.autoInstall` (boolean, default `false`) is read by `cli.js` and threaded through `build()` → image/font registries → `loadOptionalDep` in `src/install.js`. The shared helper tries the lazy `import()`; if it fails *and* `autoInstall && topDir`, it shells out to `npm install --save-dev <pkg>` in `topDir` (via the injectable `install` option, default `defaultInstallPackage`) and retries the import once. Cache semantics: each loader (`loadSharp`, `loadWawoff2`, `loadSubsetFont`) holds a module-scoped promise that's cleared on rejection, so a later call after a successful install can succeed even if an earlier one failed. Only the three known optional peer deps go through this path — user-imported npm packages (e.g. remark plugins) still fail loudly. `xtatic init` is the scaffolding command that creates/updates `topDir/package.json` to enable this flag (and to add `xtatic` to `devDependencies` if missing); see `src/init.js`.
- **Lint runs at the CLI layer, not inside `build()`.** `src/cli.js` calls `runLint({topDir, outputDir})` from `src/lint.js` *before* `build()`; a lint failure exits 1 with the formatted ESLint output and no build artifacts are written. `build()` itself stays a pure data transform with no `eslint` dependency, so memfs-injected tests are untouched (most of the suite never goes through lint). The lint phase is real-fs only — it walks the topDir tree (skipping `outputDir` and `node_modules`) and runs ESLint programmatically over `**/*.{md,mdx,jsx,js}`. Only the `cli.test.js` and `lint.test.js` real-fs scratch tests exercise the integrated lint path; all other tests bypass lint by calling `build()` directly. There is no opt-out today (no `--no-lint` flag, no `pkg.xtatic.lint: false`); add one when someone needs faster iteration.
- **The opinionated lint config** lives in `src/lint.js` `makeConfig()` and ships frozen — there is no user override yet (planned). Rule set is import-correctness only: `import/no-unresolved` (with `^xtatic:` ignored — the custom rule covers those), `import/named`, `import/no-duplicates`, `xtatic/builtin-imports` for `.md`/`.mdx`/`.jsx`/`.js`, plus `import/default` and `no-undef` for `.js`/`.jsx` only. `import/default` is **off** for `.md`/`.mdx` because xtatic's default-import semantics there bind the whole module object rather than `mm.default` (the documented divergence) — the rule would still pass since `.mdx` files always have a `default` export, but it's cheaper to disable than to reason about. `eslint-plugin-mdx` provides the `.md`/`.mdx` parser via its `flat` config preset; `eslint-plugin-import` and `eslint` are hard `dependencies`, not optional. Custom rules live under `src/eslint-rules/`. **`import/no-unresolved` uses a custom resolver, not the stock `node` one**, so xtatic's leading-`/` = `topDir` convention lints correctly instead of being read as a filesystem-absolute path (the false-positive that broke `import Foo from '/components/Foo.md'`). `src/eslint-resolver-xtatic.cjs` (CommonJS on purpose — eslint-module-utils `require()`s resolvers and the package is `type:module`) remaps a leading-`/` spec to `path.join(topDir, spec)` *only* when the importing file is `.md`/`.mdx`/`.jsx` (the extensions whose imports actually flow through `__xtatic_resolve`/`resolveSpec`), then delegates to `eslint-import-resolver-node` (now a direct dep). `.js` files are deliberately excluded — they load through Node's real `import()`, where `/foo` truly is filesystem-absolute, so lint and build agree in both directions. `makeConfig(topDir)` threads `topDir` into the resolver via its config object (eslint-module-utils only lets you name a resolver by string/path, not pass an object, so the path is computed from `import.meta.url` and the config carries `{topDir, extensions}`); broken `/`-rooted paths still report `found:false` and keep firing `no-unresolved`.
- **`.md` is parsed as MDX, not plain Markdown, by lint.** `eslint-mdx` defaults to treating only `.mdx` as MDX and `.md` as plain markdown (where `import` lines are just text and never reach the import-correctness rules). Xtatic compiles both extensions through @mdx-js/mdx, so the lint config passes `parserOptions.extensions: ['.md']` to flip `.md` into the MDX parser path. Without this, broken imports inside `layouts/default.md` (or any `.md` file) sail through lint and only blow up at render with "Unsupported JSX type: undefined". Also disables `no-unused-expressions` for `.md`/`.mdx` because the `eslint-plugin-mdx` flat preset turns it on and it false-positives on bare JSX expressions like `<Foo />` (which IS the rendered output in MDX).
- **Imports are rewritten by a recma plugin, not real `import()`.** `compile.js` calls `@mdx-js/mdx`'s `compile` directly (not `evaluate`), runs the result via `new AsyncFunction(body)`, and passes a `__xtatic_resolve` closure through `arguments[0]`. `recma-imports.js` rewrites every `await import('<spec>')` MDX produced into `await arguments[0].__xtatic_resolve('<spec>')`. The dummy `baseUrl: 'file:///xtatic/'` is required only to suppress MDX's runtime baseUrl check; it's never actually used because we removed every real `import()`. Two extra `compile` options matter: `format: 'mdx'` forces full-MDX parsing even for `.md` (without it, supplying a VFile path that ends in `.md` would flip MDX into plain-markdown mode and `import`/JSX become literal text); `development: true` makes the compiler emit `jsxDEV(…, source)` calls (the source `fileName` is the VFile path we pass — the display path) for the render-context trace. `outputFormat: 'function-body'` rewrites the generated `…/jsx-dev-runtime` import to a destructure from `arguments[0]`, so `compile.js` just needs `jsxDEV` on the runtime namespace it passes in — no real dev-runtime module.
- **`.md`/`.mdx` default-import semantics differ from ESM.** `import X from './foo.mdx'` binds X to the *whole module object*, not `mm.default`. The recma plugin enforces this by splitting the destructure: `const ns = await __xtatic_resolve(spec); const X = ns; const {a, b} = ns;` for any `default` key in the pattern. `.js` keeps standard ESM semantics (default = `.default`).
- **Cycles work via a stable placeholder identity.** `registry.js`'s `loadMdx` sets `mdxModules.set(absPath, {mm: {}, status: 'compiling'})` *before* awaiting source/compile, so a circular re-entry returns the same `mm` object reference. After compile, `Object.assign(mm, compiled)` mutates the placeholder in place — anyone holding the reference sees the final shape by render time.
- **`.js` files do not go through MDX.** They're loaded via real `import(pathToFileURL(absPath).href)`, so relative `.js`→`.js` imports and bare specifiers (npm, `node:`) resolve via Node's normal resolver. `.js`→`.md`/`.mdx` is still unsupported (Node doesn't know how to load `.mdx`). **`.js` modules also bypass the per-build registry cache invalidation** that `.md`/`.mdx`/`.jsx` get for free (those are re-read through the injected `fs` and recompiled every build): Node's ESM loader caches by URL for the *whole process*, so a fresh registry's `loadJs` still gets the first-loaded module back. `createRegistry({reloadJs})` (← `buildImpl({reloadJs})`) flips this: when set, `loadJs` appends `?v=<mtimeMs>` (from real `node:fs.statSync`, not the injected fs — `import()` reads real disk regardless) to the import URL so an edited file gets a fresh URL and re-evaluates; unchanged files keep their URL and cached module. `watch.js` passes `reloadJs: true` (so `watch`/`serve` pick up `.js` edits); one-shot `build()`/CLI build and the test suite leave it `false` (default), so their semantics — and the `import()`-caches-by-URL test gotcha below — are unchanged. **Limitation:** this only busts the *directly-imported* `.js`. A `.js` that statically imports another `.js` resolves the inner specifier through Node's resolver to a query-less URL, so transitive `.js`→`.js` edits still don't reload — touch the directly-imported file. (Full transitive reload would need a `module.register` resolve hook; deliberately not done for a dev-only convenience.)
- **`.jsx` files have their own compile pipeline in `src/compile-jsx.js`.** They're parsed with `acorn` extended by `acorn-jsx` (with `locations: true` so JSX nodes carry `loc`), JSX is lowered by `estree-util-build-jsx` (automatic runtime, `importSource: '__xtatic_internal_jsx_runtime'`, `development: true` + `filePath` so it emits `_jsxDEV(…, source)` like the `.mdx` path), `transformModule` strips the auto-import (re-emits it as a destructure from `arguments[0]` — its match accepts both `…/jsx-runtime` and `…/jsx-dev-runtime`), expands user `ImportDeclaration`s into MDX-style `await import(...)` patterns so `recmaImports` can rewrite them, and rewrites `export` declarations into a single `return { … }` statement. Then `astring` serializes and the body runs in `new AsyncFunction(body)`. Same dependency footprint as `.mdx` — no new direct deps; `acorn`, `acorn-jsx`, `estree-util-build-jsx`, and `astring` are all transitive via `@mdx-js/mdx`.
- **`.jsx` differs from `.mdx` deliberately.** No `recma-self` (so module properties don't leak as bare identifiers — pure JS scoping), no frontmatter, no markdown body. Default-import semantics are ESM (`import X from './x.jsx'` binds `X` to `mm.default`), the same as `.js` and unlike `.md`/`.mdx`. `.jsx` files are also **not auto-promoted to pages** — `walkMdx` ignores them; they only enter the build via `import`. Builtins (`html`, `readfile`, `asset`) work identically to `.mdx`: import from `xtatic:builtins`, no ambient binding. recma-assets runs in `compile-jsx.js` too (after `recmaImports`, before code generation), so plain `<img>`/`<link>`/etc. inside `.jsx` get the same auto-asset processing.

## JSX shim cheat sheet

`src/jsx-runtime.js` returns `{html: string}` directly — no VDOM. Exports `jsx`, `jsxs` (alias), `Fragment`, and `jsxDEV`. Both compile pipelines run in `development` mode, so user JSX always calls `jsxDEV(type, props, key, isStaticChildren, source)` — it forwards to `jsx` but, for component/module `type`s (not string elements), pushes a render-context frame carrying the call site from `source` and `attachContext`s any throw. `jsx`/`jsxs` are still used internally by `render.js`'s layout walk. Tag types: string (HTML element), function (component), or module object (calls `mm.default`). Children: HTML objects pass through unescaped; modules render via `mm.default({})` (and, if they carry `__xtatic_path`, get a render-context frame); primitives are HTML-escaped; null/undefined/booleans render empty; arrays flatten. Attribute renames: `className` → `class`, `htmlFor` → `for`. Booleans use HTML conventions (bare on `true`, omitted on `false`/`null`/`undefined`).

## Workflow

- `npm test` runs the full Node test suite. Three flavors:
  - **memfs tests** (most of them) inject a memfs `fs`; nothing touches disk.
  - **real-fs tests** (`test/cli.test.js`, `test/imports-js.test.js`, `test/smoke.test.js`, `test/remark-plugins.test.js`) scratch under `./test-tmp/<file>/...`. Each file's top-level `before` wipes only its own subtree (test files run in parallel, so a file-wide wipe of `test-tmp/` will race other files' fixtures). `test-tmp/` is gitignored. Slugs must be unique per test in the file — Node caches `import()` by URL, so reusing a slug serves stale `.js` content.
  - The smoke test passes no fs injection, exercising the default `node:fs` code path end-to-end.
- **Commit changes directly to `main` as you make them, once tests pass — don't wait to be asked.** No branches, no PRs. Splitting a change into several commits is fine, as long as the suite is green for each one. Don't batch unrelated changes; checkpoint often. Don't push after committing.
- **Before committing a user-visible change, update `README.md`** — new builtins, new exports (e.g. `outputPath`), new `pkg.xtatic.*` options, new CLI flags, changes to the input→output mapping, or removed features. Internal refactors and test-only changes don't need a README touch. CLAUDE.md captures invariants for future-me; README is the user contract — both should land in the same commit as the code so a `git show` is self-contained.
- ESM only — `package.json` has `"type": "module"`, all imports use explicit `.js` extensions.

## Known scope cuts (deliberate)

- `style` prop accepts strings only; object form (`style={{color: 'red'}}`) stringifies as `[object Object]`.
- Components are synchronous; async MDX components aren't supported.
- POSIX path separators only; not tested on Windows.
